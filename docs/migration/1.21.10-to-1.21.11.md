# Migration gotchas: 1.21.10 → 1.21.11 (roadmap M6)

Companion to [`1.21.8-to-1.21.10.md`](1.21.8-to-1.21.10.md). Target: **MC 1.21.11 / NeoForge 21.11.48**, Parchment
`1.21.11 / 2025.12.20` (the last Parchment release — 26.x ships unobfuscated), JEI `27.55.0.122`; nothing folded in.
Branch `1.21.11` in both repos. Upcoming release: Mantle `1.17` / Tinkers `3.16.0` (tags `v1.21.11-1.17` /
`v1.21.11-3.16.0`). Plan: `tinkers/docs/superpowers/plans/2026-11-25-m6-1.21.11-port.md`.

1.21.11 is the widest mechanical bump of the series and one of the cheapest in judgment. The compiler found **1172 errors
in Mantle** (M5: 100) and **3570 in Tinkers** (M5: 594); 849 of Mantle's were the `ResourceLocation` → `Identifier`
rename and 156 the removed vanilla `MethodsReturnNonnullByDefault` in `package-info.java`. The new rename-map scripts
brought them down to **145 (Mantle) and 221 (Tinkers)** before any hand fix. The real cost was elsewhere and silent:
**baked quads without `int[]`**, **render types on `RenderSetup`**, and the **item atlas split** (item textures left the
blocks atlas), which compiles and renders missing or wrong sprites. Fixing the atlas fallout also showed that **worn
Tinkers armor had rendered as vanilla iron armor since 1.21.4** (see [Release bugs](#release-bugs-found-during-m6-that-affect-earlier-lines)).

## Target choice & toolchain

- NeoForge 21.11 is stable since `21.11.42`; `21.11.48` is the newest stable build. JEI keeps a maintained 1.21.11 line
  (`27.55.0.122`, new major), so 1.21.11 gets its own checkpoint (26.1/26.1.1 fold into M7 = 26.1.2).
- Toolchain unchanged: NeoGradle **7.1.39** + Gradle **9.2.1**, Java 21 (MC 1.21.11 `javaVersion` = 21). NeoForm
  `1.21.11-20251209.172050` decompiles and recompiles with it.
- Pins: Crafting Tweaks `21.11.5` + Balm `21.11.9.1` (the `+mc` suffix is gone from both version schemes; Balm pulls
  `kuma-api-neoforge 21.11.12` through the existing `net.blay09.mods` filter), JSON Things `0.17.0`. Immersive
  Engineering stays excluded (1.21.1 only). No `build.gradle` change: every artifact name derives from the properties.
- FML 10.0.36: `FMLEnvironment.getDist()/isProduction()` and `FMLLoader.getCurrent()` all still exist — the
  "`FMLLoader.isProduction()` removed" note in some summaries does not apply to us.

## The `Identifier` rename (and the scripts that do it)

Mojang renamed `net.minecraft.resources.ResourceLocation` to **`Identifier`**. It is a pure type-token swap: every
static factory and member keeps its name (`fromNamespaceAndPath`, `parse`, `tryParse`, `tryBuild`, `withDefaultNamespace`,
`withPath/withPrefix/withSuffix`, `CODEC`, `STREAM_CODEC`, …). JSON and data files don't change.

| 1.21.10 | 1.21.11 |
|---|---|
| `net.minecraft.resources.ResourceLocation` | `net.minecraft.resources.Identifier` |
| `net.minecraft.ResourceLocationException` | `net.minecraft.IdentifierException` |
| `commands.arguments.ResourceLocationArgument` | `commands.arguments.IdentifierArgument` (`id()`, `getId(ctx, name)`) |
| `ResourceLocation.isAllowedInResourceLocation(char)` | `Identifier.isAllowedInIdentifier(char)` |
| `FriendlyByteBuf#readResourceLocation()` / `writeResourceLocation(…)` | `readIdentifier()` / `writeIdentifier(…)` |
| `ResourceKey#location()` | **`ResourceKey#identifier()`** |
| `TagKey#location()`, `SoundEvent#location()` | **unchanged** (`TagKey` is a record `(registry, Identifier location)`) |

**⚠️ The `.location()` rename depends on the receiver type.** A regex over `.location()` would break every `TagKey` and
`SoundEvent` call. We ran it **compiler-driven**: only the lines where javac reported `cannot find symbol method
location()` on a `ResourceKey` (Mantle 42, Tinkers 101 lines). Guard: unit `TagConditionCodecTest` (tag conditions
encode the exact registry and tag ids).

### Recipe we followed (decisions D-R1 / D-R2)

1. **Token swap by script, per repo, in its own commit** (no logic change in it): `\bResourceLocation\b` → `Identifier` in
   every `src/**/*.java` (main, test, gametest, uitest, datagen), **comments and javadoc included** (a stale
   `{@link ResourceLocation}` breaks javadoc). Word boundaries leave our own `*ResourceLocation*` names alone. Same script:
   the exception/argument/`isAllowed…`/`FriendlyByteBuf` renames above. Review the diff for string literals (0 real hits).
2. **Compiler-driven pass** for `ResourceKey#location()` → `identifier()` (own commit).
3. Fix the cascades by hand (record canonical constructors, erasure clashes, "does not override").
4. **Keep the public Mantle/Tinkers names** (D-R2): `ResourceLocationLoadable`, `ResourceLocationSerializer`,
   `Loadables.RESOURCE_LOCATION`, `JsonHelper.getResourceLocation/parseResourceLocation`, `BookRepository.getResourceLocation`,
   fields and parameters named `*location*`. They now take/return `Identifier`. Renaming them would only add downstream
   churn and make backports to the 1.21.1–1.21.10 lines harder. Forced renames only where we override a renamed
   vanilla/JEI method (JEI `getIdentifier`).

### Tooling: `repo/scripts/rename-map/`

- **`Invoke-RenameMap.ps1`** applies a map file (`maps/1.21.11.txt`, rules `token`/`literal`, top to bottom) to
  `src/**/*.java`; dry run by default (hits per rule/file, string-literal warnings), `-Apply` keeps line endings and BOMs.
  Tinkers runs it from `../repo/scripts/rename-map/`. Commands: [`COMMANDS.md`](../COMMANDS.md#mechanical-renames-between-versions-rename-map).
- **`Find-MovedClasses.ps1 -Root <repo> -Jar <raw.jar>`** lists every `net.minecraft`/`com.mojang` import of a repo that
  no longer exists in the target jar (NeoForm's `build/neoForm/neoFormJoined<version>-*/raw.jar`) and prints a
  `literal` rule when exactly one class with the same simple name exists. Primers are non-exhaustive about moved classes;
  this seeded Tinkers' 33 moved classes into the map.
- **`Convert-PackageInfoToNullMarked.ps1`** rewrites `package-info.java` (see [Nullability](#nullability-annotations)).
- Result: **Mantle 1172 → 145, Tinkers 3570 → 221 unique errors** after the scripts, before any hand fix.

### ⚠️ The access transformer is not touched by the rename-map

The scripts only read `src/**/*.java`. `accesstransformer.cfg` names classes and JVM descriptors
(`Lnet/minecraft/resources/ResourceLocation;`, `advancements/critereon/…`, moved classes). An entry whose target no longer
exists does not fail the build: NeoGradle logs a warning and goes on, and code that touches the member fails with an
access error at the call site (or not at all, e.g. a widened member only reached through a subclass or reflection).
Tinkers' AT (106 entries at the time) was retargeted by hand and **every entry checked against the 1.21.11 jar**
(`8da901bd8d`): the four arrow classes moved to `projectile.arrow`, descriptors updated for `advancements.criterion`,
`Identifier`, the 4-arg `AbstractContainerScreen#renderSlot` and `FishingHookRenderer#stringVertex`, and the
`RenderStateShard`/`CompositeRenderType` entries dropped (classes removed). Mantle's 9 entries needed no change. Guard for
the arrow fields: gametest `longbow_arrow_damage_and_pierce` (in dev the AT is baked into the recompiled jar, so it guards
behaviour, not FML's runtime AT application). A checker script exists only in the M6 scratchpad — candidate for
`repo/scripts/`.

## Nullability annotations

- Vanilla `net.minecraft.{FieldsAreNonnullByDefault, MethodsReturnNonnullByDefault}` (and the `com.mojang.blaze3d` /
  `com.mojang.math` copies) are **removed**, which breaks every `package-info.java` that used them. Vanilla and NeoForge now
  mark packages with JSpecify **`@NullMarked`** and use type-use `org.jspecify.annotations.Nullable`.
- **D-N1:** our `package-info.java` files (Mantle 79, Tinkers 278) replace the `@ParametersAreNonnullByDefault` +
  `@MethodsReturnNonnullByDefault` pair with `@NullMarked`, by script, in its own commit. Same meaning (non-null unless
  `@Nullable`), now also for fields.
  ```java
  // 1.21.10
  @ParametersAreNonnullByDefault
  @MethodsReturnNonnullByDefault
  package slimeknights.mantle.util;
  import javax.annotation.ParametersAreNonnullByDefault;
  import net.minecraft.MethodsReturnNonnullByDefault;
  // 1.21.11
  @NullMarked
  package slimeknights.mantle.util;
  import org.jspecify.annotations.NullMarked;
  ```
- **jsr305 still compiles.** `com.google.code.findbugs:jsr305:3.0.2` is on the compile classpath because **NeoForm
  1.21.11 lists it in its `libraries`** — not through Minecraft any more (MC 1.21.11's Guava 33.5.0 depends on JSpecify
  instead). `org.jspecify:jspecify:1.0.0` and `org.jetbrains:annotations:26.0.2-1` come the same way. **Recheck at M7
  Phase 0**: the day NeoForm drops jsr305, every `javax.annotation` import breaks.
- **D-N2: the `javax.annotation.Nullable` → JSpecify `@Nullable` migration is deferred** (to an optional phase or M7). It
  is not mechanical: type-use placement differs (`Outer.@Nullable Inner`, `Object @Nullable []`, fully qualified types).
  `javax.annotation.Nullable` keeps working under `@NullMarked`. New code that needs a type-use annotation uses JSpecify
  (e.g. `List<@Nullable ItemStack>` in `EntityIngredient#getEggs`).

## Rendering

### Render types: `RenderSetup` replaces `RenderStateShard`

- `RenderStateShard` and `RenderType.CompositeState` are gone; `RenderType` moved to
  `net.minecraft.client.renderer.rendertype` and is built from a **`RenderSetup`**: `RenderSetup.builder(RenderPipeline)` →
  `withTexture(sampler, Identifier[, Supplier<GpuSampler>])`, `useLightmap()`, `useOverlay()`, `affectsCrumbling()`,
  `sortOnUpload()`, `bufferSize(int)`, `setLayeringTransform(…)`, `setOutputTarget(…)`, `setTextureTransform(…)`,
  `setOutline(…)`, `createRenderSetup()`; then `RenderType.create(name, setup)`.
- Vanilla's types moved to **`RenderTypes`** (`entitySolid/entityCutout/entityCutoutNoCull/entityTranslucent/
  itemEntityTranslucentCull/text/lines()/blockScreenEffect`, …); `solid/cutout/tripwire` became
  `solidMovingBlock/cutoutMovingBlock/tripwireMovingBlock`. `RenderPipelines.SOLID/CUTOUT/TRIPWIRE` → `*_BLOCK`/`*_TERRAIN`,
  `TRANSLUCENT` → `TRANSLUCENT_TERRAIN`, `CUTOUT_MIPPED` removed.
- Rebuild custom types **property by property** on the same pipeline (D-RT): Mantle `FLUID` / `TRANSLUCENT_FULLBRIGHT` and
  Tinkers `ERROR_BLOCK` / `SMELTERY_FLUID` keep names, pipelines, buffer size 256, sort-on-upload, lightmap/overlay and
  outline flags. A missing `useLightmap()` or texture binding compiles and draws black or invisible geometry.
  ```java
  public static final RenderType FLUID = RenderType.create(Mantle.modId + ":block_render_type",
    RenderSetup.builder(MantleShaders.getConfiguredFluidPipeline())
      .useLightmap()
      .withTexture("Sampler0", TextureAtlas.LOCATION_BLOCKS, BLOCK_SHEET_MIPPED_SAMPLER)
      .sortOnUpload()
      .bufferSize(256)
      .createRenderSetup());
  ```
- **Sampler parity:** the old `BLOCK_SHEET_MIPPED` shard was the NEAREST block atlas with mipmaps
  (`NEAREST_MIPMAP_LINEAR` min, `NEAREST` mag). Vanilla's `RenderTypes.MOVING_BLOCK_SAMPLER` uses a LINEAR min filter, so it
  is **not** a drop-in: Mantle and Tinkers use `RenderSystem.getSamplerCache().getClampToEdge(FilterMode.NEAREST, true)`.
- **Line width moved to the vertices** (`VertexConsumer#setLineWidth`; `ShapeRenderer.renderShape(…, lineWidth)`). The AOE
  outline, the smeltery error block and the fishing line pass the width vanilla uses (`Window#getAppropriateLineWidth()`
  for `lines()`).
- `FluidRenderer#renderCamera` draws through `RenderTypes.blockScreenEffect` like vanilla `ScreenEffectRenderer`.
  Also: `Camera#getPosition()` → `position()`, `TextureSetup.singleTexture` takes the atlas texture's sampler, sprite
  suppliers implement `SpriteSource.DiscardableLoader`.

### Baked quads are records

- `record BakedQuad(Vector3fc position0..3, long packedUV0..3, int tintIndex, Direction direction, TextureAtlasSprite
  sprite, boolean shade, int lightEmission, BakedNormals bakedNormals, BakedColors bakedColors, boolean
  hasAmbientOcclusion)` — the last three are NeoForge's; **vanilla's 13-arg constructor silently defaults them**
  (`UNSPECIFIED` / `DEFAULT` / `true`). Readers use `position(i)` / `packedUV(i)` (`UVPair.unpackU/V`) instead of `int[]`
  offsets. Copying a quad means copying **every** field (Tinkers' casting fade copies all and only swaps the tint index;
  Mantle `ModelHelper.withColors(quad, colors)`).
- NeoForge **`IQuadTransformer` / `QuadTransformers` are removed** → `UnaryOperator<BakedQuad>` (Mantle's `bakePart`
  overloads; `UnaryOperator.identity()` where `QuadTransformers.empty()` was used) or `QuadTransforms.applyTransformation`.
  Per-vertex colors/normals go through NeoForge `client.model.quad.BakedColors` (`of(argb)`, `of(×4)`) and `BakedNormals`.
  Mantle `ColoredBlockModel.applyColorQuadTransformer` now sets ARGB `BakedColors` instead of ABGR vertex colors.
- `FaceBakery.bakeQuad(ModelBaker.PartCache, from, to, face, sprite, direction, state, rotation, shade, lightEmission)`:
  inside the bakery use `modelBaker.parts()`, outside it Mantle's `ModelHelper.UNCACHED_PARTS`.
- **The per-vertex lightmap (UV2) is gone.** Emissivity becomes the quad's `lightEmission` (max per channel at render time —
  same result as the old baked UV2; possible one-level banding on luminous faces under smooth lighting, as in vanilla).
- **⚠️ NeoForge `QuadBakingVertexConsumer` ignores `setUv2` and resets the sprite and light emission after each quad.**
  Set luminosity with `setLightEmission` and set the sprite again before every quad (Mantle `MantleItemLayerModel`).
- `BlockModelRotation` is a class now: `X0_Y0` → `IDENTITY`, no `values()` (`get(OctahedralGroup)`, built from
  `Quadrant.fromXYAngles`). NeoForge `RenderTypeGroup#entity()` → `entityBlock()` / `entityItem()` (see the atlas split).

## Item atlas split (silent)

1.21.11 gives items their own atlas. Vanilla `assets/minecraft/atlases/blocks.json` now sources only `block/` (+ conduit,
bell, enchanting book); `items.json` sources **every namespace's `item/`** plus the item trim permutations. New:
`AtlasIds.ITEMS` (`minecraft:items`), `TextureAtlas.LOCATION_ITEMS`, and `ModelManager.BLOCK_OR_ITEM`
(`minecraft:block_or_item`), the pseudo atlas vanilla assigns to **every texture parsed from a model JSON** — the model
bakery's sprite getter looks in the items atlas first, then blocks. Nothing fails at compile time: an `item/…` texture
looked up on the blocks atlas just renders the missing sprite.

- **⚠️ `AtlasManager#get(Material)` throws on `BLOCK_OR_ITEM`** ("Invalid atlas texture id"). Runtime lookups of model
  textures go through Mantle **`ModelHelper.getSprite(Material)`** (items first, then blocks, like the bakery). Mantle's
  `NBTKeyModel.Baked#getTexture` now returns the concrete atlas the sprite was baked from (Tinkers' JEI slot renderer
  crashed on the pseudo atlas).
- **A layer binds one atlas.** Item render types must match the atlas of their quads: blocks atlas →
  `Sheets.cutoutBlockSheet()` / `translucentBlockItemSheet()` / `RenderTypeGroup#entityBlock()`, items atlas →
  `Sheets.translucentItemSheet()` / `entityItem()` (Mantle `ModelHelper.getDefaultItemRenderType(stack, quads)`, replicating
  vanilla `BlockModelWrapper#detectRenderType`, and `getEntityRenderType(group, quads)`, replicating NeoForge
  `RenderTypeHelper`). Quads that mix atlases (retextured items, fluid containers: bucket/mask textures moved to items,
  fluids stay on blocks) need **one layer per atlas** → Mantle **`ModelHelper.addItemLayers(…, RenderTypeGroup, …)`**.
  ```java
  // 1.21.10: one layer, one render type
  ModelHelper.addItemLayer(renderState, stack, context, quads, properties, renderType, extents, animated);
  // 1.21.11: pass the model's render type group; mixed quads become one layer per atlas
  ModelHelper.addItemLayers(renderState, stack, context, quads, properties, renderTypeGroup, extents, animated);
  ```
  `addItemLayer` with a `null` render type delegates to `addItemLayers`; with an explicit render type it cannot split and
  logs a warning once per model. Tinkers' `ItemModelUtil.BakedItem` holds the model's `RenderTypeGroup`
  (`defaultRenderType()` → `defaultRenderTypes()`).
- **Draw-order limitation:** `addItemLayers` groups quads by atlas in order of first appearance, so a quad from the second
  atlas draws after **all** quads of the first one. No Tinkers model draws anything after an items-atlas trim, but an addon
  model relying on interleaved order across atlases will draw differently.
- **Tinkers keeps tool sprites on the blocks atlas.** Its generated `blocks.json` adds `item/tool/`, `fluid/`,
  `gui/modifiers/` and `gui/tinker_pattern/` (tool models mix tool sprites with block-atlas fluid sprites in one quad list).
  Because vanilla's items atlas also picks up every `item/`, the ~11k `item/tool/` sprites (≈21 MB) were stitched twice;
  a generated `assets/minecraft/atlases/items.json` filters them out again:
  ```json
  { "sources": [ { "type": "minecraft:filter", "pattern": { "namespace": "^tconstruct$", "path": "^item/tool/" } } ] }
  ```
  **⚠️ `IdentifierPattern` uses find semantics** — an unanchored `item/tool/` matches anywhere in the path; anchor it.
  Pack atlas sources apply after vanilla's, and `BLOCK_OR_ITEM` lookups fall back to blocks, which reproduces 1.21.10.
- Other `item/…` lookups that used `LOCATION_BLOCKS` move to the items atlas or `BLOCK_OR_ITEM` per call site (D-ATLAS):
  Tinkers modifier icons pointing at `minecraft:item/…` / `item/materials` (items first, then blocks), fluid container
  models (base/mask/particle as model JSON textures), material block models.
- **"Duplicate sprite" across atlases:** stitching a texture that vanilla already puts on the items atlas into the blocks
  atlas too logs one warning per sprite ("to be rejected in a future version"). We hit it with the trim permutations
  (64 warnings) — see below. The client log check is "0 Duplicate sprite, 0 missing textures".
- `TextureAtlas.LOCATION_BLOCKS/ITEMS` are vanilla-deprecated with no replacement (warnings only).
- Guard: uitest `item_atlas_grid` (copper can/tank fluid layers, material-less parts, molten buckets, `minecraft:item`
  modifier icons; asserts the icon textures resolve via `BLOCK_OR_ITEM`), plus `dynamic_item_icons`.

## Trims and worn armor

### Trims

- **Vanilla's item trim permutations moved to the items atlas** (`trims/items/*_trim_<material>`, `paletted_permutations`
  in `items.json`). Tinkers' `TrimModifierModel` looked them up on the blocks atlas → flat tint + a WARN per material.
  First fix (Phase 3) re-stitched them into the blocks atlas, which produced the 64 duplicate-sprite warnings; final fix
  (`16234c5324`): look the icon up on the **items atlas first, then blocks** (Tinkers' own trim palettes and custom trim
  roots stay on blocks). With `addItemLayers` the trim becomes its own layer drawn after the tool.
- **Worn trim textures moved in vanilla 1.21.4** from `trims/models/armor/<pattern>(_leggings)` to
  `trims/entity/humanoid(_leggings)/<pattern>`. Tinkers' `TrimArmorTextureSupplier` and the `armor_trims` atlas source
  still used the old paths, so every trimmed Tinkers armor piece fell back to a tint of a missing texture — a port bug
  since 1.21.4, fixed in `670833fa4b`. Worn trims use vanilla's decal render type for decal patterns; Tinkers' custom
  trim icons got the resin palette added in 1.21.4.
- Guard: uitest `trimmed_armor` (worn + carried plate armor with iron/gold/resin/cobalt trims; asserts the trim data, every
  item icon sprite incl. `*_darker`, that vanilla palettes are on the items atlas and not duplicated on blocks, and every
  worn sprite on the armor trims atlas; pixel asserts on the copper helmet / iron trim band / gold leggings).

### Worn armor: equipment asset + Tinkers' own layer

Since the 1.21.4 port, worn plate/travelers/slime armor and the slimeskull rendered as **vanilla iron armor**:
`humanoidArmor(ArmorMaterials.IRON, …)` gave every piece the `minecraft:iron` equipment asset, and the armor model
dispatchers were never registered nor called (the custom armor model hook can no longer composite dynamic layers). The
fix has four parts, each forced by a vanilla check:

1. **The equipment asset must exist.** `HumanoidArmorLayer.shouldRender` requires `Equippable#assetId()` to be present,
   and `HumanoidMobRenderer` copies a worn stack into the render state only then — **an asset-less `Equippable` never
   reaches the render state**, so a layer of our own would see nothing.
2. **It must have layers.** The equipment asset codec is a `nonEmptyMap`, and vanilla `CapeLayer` offsets/hides the cape by
   looking at the chestplate's layers. `tconstruct:tinker_armor` (`assets/tconstruct/equipment/tinker_armor.json`) has one
   `humanoid` layer on a transparent texture; `tconstruct:tinker_wings` adds a transparent `wings` layer so the cape hides
   under always-winged chestplates (slime).
3. **Vanilla must draw nothing for it.** `ArmorModelDispatcher#getArmorLayerTintColor` returns `0` for every asset layer,
   so vanilla's equipment layer submits nothing — not even its glint. Tinkers never sets `DataComponents.TRIM`, so there is
   no double trim. Stats are an exact iron copy with only the asset changed.
4. **Tinkers draws it:** `TinkerArmorLayer` is inserted after **every** `HumanoidArmorLayer` (`AddLayers`: player skins and
   entity types — mannequins, armor stands, zombies, skeletons, piglins…; 2 AT entries for its model sets) and submits the
   `ArmorTextureSupplier` layers: tint + luminosity, trims incl. decals, glint on the first layer, elytra-modifier wings,
   and the slimeskull's material head.

Only armor drawn from an armor model (`MultilayerArmorItem`, slimeskull) uses `tinker_armor`. **A plain
`ModifiableArmorItem` (JSON Things `basic_armor`) keeps `minecraft:iron`** — it has no armor model nor dispatcher, so the
empty-looking asset made it invisible (found by review). Guards: gametests `armor_equipment_assets` and
`jsonthings_armor_equipment_assets`, uitests `trimmed_armor` and `worn_armor` (armor stands + a zombie, pixel asserts,
scenario-owned entities); mutation-checked (layer not drawing → both uitests fail).

## GUI

- `Screen#minecraft` / `font` are **final**, set by `Screen(Component)` (or `Screen(Minecraft, Font, Component)`);
  `init(Minecraft, int, int)` → `public final init(int, int)` + `protected init()`; `resize(Minecraft, int, int)` →
  `resize(int, int)`.
- `AbstractContainerScreen#renderSlot(GuiGraphics, Slot, int mouseX, int mouseY)`.
- `Button` is abstract (`Button.Plain` is the old button; `Button.builder(…).build()` returns one).
  `AbstractButton#renderWidget` is **final** → override `renderContents(GuiGraphics, int, int, float)` and call
  `renderDefaultSprite`/`renderDefaultLabel` if you want vanilla's look. Buttons now show the **hand cursor** on hover
  (vanilla `AbstractButton` behaviour — Mantle `ArrowButton` and the Tinkers station buttons, accepted).
- `GuiGraphics(Minecraft, GuiRenderState, int mouseX, int mouseY)` — Mantle's offscreen book export passes `(-1, -1)`.
- `Font#wordWrapHeight(String, int)` is gone; the `FormattedText` overload counts a trailing newline as an extra line, so
  book content uses Mantle `PageContent.wordWrapHeight(Font, String, int)` (splits like the removed overload).
- `InventoryScreen#renderEntityInInventory` is gone (Tinkers' Tool Table armor-stand preview submits its render state
  directly).
- `AbstractContainerScreen#keyPressed` returns **`false`** when the screen didn't handle the key. The Phase 4 sweep of
  Tinkers' container screens found nothing that relied on `true`.

## Commands, game rules, level

### Permissions

`CommandSourceStack#hasPermission(int)` and `Player#hasPermissions(int)` are **removed**. Permissions are
`net.minecraft.server.permissions`: a `PermissionSet` (`CommandSourceStack#permissions()`, `Player#permissions()`) checked
against `Permission`s (`Permissions.COMMANDS_MODERATOR/GAMEMASTER/ADMIN/OWNER`); `Commands.LEVEL_*` are `PermissionCheck`s.

Mantle applies the **R2 vocabulary rule** (op level is a stable domain concept): the public `int` constants
`MantleCommand.PERMISSION_EDIT_SPAWN` (1) / `PERMISSION_GAME_COMMANDS` (2) / `PERMISSION_PLAYER_COMMANDS` (3) /
`PERMISSION_OWNER` (4) **stay**, and Mantle adds helpers that map them to the vanilla permissions (≤ 0 always passes, > 4
never does), so downstream code never names the vanilla permission types:

```java
// 1.21.10
builder.requires(source -> source.hasPermission(MantleCommand.PERMISSION_GAME_COMMANDS));
if (player.hasPermissions(2)) { … }
// 1.21.11
builder.requires(source -> MantleCommand.hasPermission(source, MantleCommand.PERMISSION_GAME_COMMANDS));
if (MantleCommand.hasPermission(player, MantleCommand.PERMISSION_GAME_COMMANDS)) { … }
```

Tinkers' 9 subcommands and the `CreativeSlotItem` / `ModifierCrystalItem` op checks use the helpers. Guard:
`PermissionGameTests` (every op level pair for source and player, `/tconstruct durability` op 2, `/tconstruct report` and
`/mantle tags preference` op 1, quick apply and crystal removal op 2 with the survival config on/off).

## Compat (JEI 27, Crafting Tweaks, JSON Things)

### JEI 27

API diff method as in M4/M5 (`javap -public` of common-api + neoforge-api 26.3.0.31 → 27.55.0.122; the jars live under
the scoop Gradle home `C:\Users\aleja\scoop\apps\gradle\current\.gradle\caches`). Removals were already absorbed in M5;
most of the diff is the `Identifier` rename. The behaviour changes are the dangerous part:

- **`IRecipeCategory#getIdentifier`** is what JEI 27 calls; `getRegistryName` is deprecated and only delegates to it.
  ⚠️ Our 8 `getRegistryName` overrides **compiled and were never called** (ids fell back to JEI's `RecipeHolder`-only
  default) — renamed in `f17e105425`.
- `IIngredientHelper#getIdentifier(V)` is abstract (`getResourceLocation` a deprecated default); `getTagStream` returns
  `Stream<Identifier>`.
- **Renderers/tooltips:** JEI 27 only calls `IIngredientRenderer#render(GuiGraphics, T, x, y, IIngredientRenderContext)`
  and `getTooltip(T, Item.TooltipContext, Player, TooltipFlag)`. The old `render(GuiGraphics, T)` / `getTooltip(T,
  TooltipFlag)` are deprecated for removal **but still abstract**, so each renderer keeps a minimal
  `@SuppressWarnings("removal")` delegate (2 in Mantle, 8 in Tinkers; Tinkers' 2 legacy transfer overloads below are the
  other suppressed delegates).
- **Transfers:** JEI calls `IRecipeTransferHandler#transferRecipe(IRecipeTransferContext, doTransfer)` (legacy overload
  still abstract). Tinkers' station and tool inventory handlers validate/trim the recipe slots and hand JEI's basic handler a
  context (`FilteredRecipeTransferContext` when trimmed), so transfers use the result-reporting packets and fire JEI's
  transfer listeners.
- **⚠️ JEI 27 drops empty stacks** from an ingredient list and **validates focus-link slot sizes** while indexing. Mantle
  `EntityIngredient#getEggs` mapped egg-less entities (the player…) to `AIR`, so the entity and egg slots of entity melting /
  severing recipes differed in size → logged as broken recipes, never laid out. Now a **`null` entry** (JEI keeps it as an
  empty position) and Tinkers passes the hidden egg slot through `addIngredients(VanillaTypes.ITEM_STACK, …)`, whose list
  elements are nullable.
- **⚠️ Ingredient removals match the grouping uid** (uid without subtype), and JEI 27 **hides recipes whose focus-linked
  slots only show removed ingredients**. Removing the variantless potion fluid removed every potion variant → 342 potion
  casting/tipping recipes vanished. The variantless potion now has its own `"none"` subtype.
- Accepted: JEI 27 hides fills of the ~30 absent-compat / tag-hidden fluids (124 table / 310 basin recipes) — consistent
  with Tinkers hiding those fluids.
- JEI `[removal]`/`[deprecation]` warnings: Mantle 2 → 0, Tinkers 27 → 0. Guards: uitest `jei_tinker_station_transfer`,
  `jei_tool_inventory_transfer`, `jei_recipe_transfer` (requires `RecipeTransferResult.SUCCESS`), `jei_category_tooltips`
  (every ingredient renderer tooltip), the entity scenarios fail when a recipe cannot lay out, and the casting categories
  pin their visible recipe counts (table ≥ 1735, basin ≥ 706).

## Verification lessons

- **The scripts are worth it.** The rename-map + `Find-MovedClasses` + `@NullMarked` converter turned 1172/3570 errors into
  145/221 in a few reviewable commits; the compiler-driven `identifier()` pass took 46/106 more. Keep the mechanical commits
  pure so review can skip them.
- **The silent breaks came from outside the compiler:** the item atlas split (missing sprites), worn armor drawn as iron
  since 1.21.4, worn trims on 1.21.4 paths, JEI's `getIdentifier` (8 overrides never called), JEI 27 dropping empty stacks,
  and the AT that the rename never sees. Each now has a guard: `item_atlas_grid`, `trimmed_armor`, `worn_armor`,
  `armor_equipment_assets`, the JEI transfer/tooltip/layout scenarios, `longbow_arrow_damage_and_pierce`.
- **Pixel asserts beat screenshots for "did it draw".** `trimmed_armor`/`worn_armor` sample specific pixels and check the
  material; mutation-checked (layer off → red).
- **The reference run still matters but found little:** the 1.21.10 reference run (43/43) vs the 1.21.11 run, every PNG
  pair reviewed — no regression in the 42 shared scenarios (diffs = JEI 27 layout, animation frames, cursor).
- **Independent review after every batch** caught: `NBTKeyModel#getTexture` exposing `block_or_item` materials (crash),
  mixed-atlas item layers, the sampler filter mismatch (Phase 1c); the vanilla trim regression (Phase 2B); the invisible
  JSON Things plain armor and the cape (Phase 4).
- **Boundary contracts first** (R1, Phase 0.5): the new client-sync, handler-registration and golden-diff guards were
  proven on 1.21.10 (and mutation-checked) before the port, so a red during the port meant a port bug.
- uitest still needs an **unlocked screen** (`atio6axx.dll` at `glfwCreateWindow` while Windows is locked).

  plate chestplate with the elytra modifier uses `tinker_armor` (no wings layer) and the cape still draws.
- **Legacy modifier-model loader `tconstruct:trim` is unregistered since 1.21.4** (`ToolClientEvents:176` `PORT 1.21.4`
  breadcrumb; log "Skipping modifier tconstruct:trim"). Only addon tools on legacy modifier models lose the trim icon.

  across atlases draw differently.
