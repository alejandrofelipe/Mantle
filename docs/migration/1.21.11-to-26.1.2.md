# Migration gotchas: 1.21.11 → 26.1.2 (roadmap M7)

Companion to [`1.21.10-to-1.21.11.md`](1.21.10-to-1.21.11.md). Target: **MC 26.1.2 / NeoForge 26.1.2.130**, **Java 25**,
no Parchment (26.1 ships unobfuscated), JEI `29.54.0.123`. **26.1 and 26.1.1 are folded in** (NeoForge was beta-only
there). Branch `26.1.2` in both repos. Upcoming release (D-REL): Mantle `1.18` / Tinkers `3.17.0` (tags `v26.1.2-1.18` /
`v26.1.2-3.17.0`). Plan: `tinkers/docs/superpowers/plans/2026-11-26-m7-26.1.2-port.md`.

26.1.2 is a smaller mechanical bump than 1.21.11 and a much deeper semantic one. The compiler found **770 unique errors in
Mantle** (M6: 1172) and **1246 in Tinkers** (M6: 3570; main sources, before the test sources could compile). The jar-diff
rename tools took them to **237 / 647** before any hand fix. The real cost was silent: **stacks need bound data components**
(recipes, loot, advancements, datagen, static init and unit tests can no longer build an `ItemStack`/`FluidStack`), **render
layers are per quad** (NeoForge dropped `render_type` from the model format), **fluid client data moved into `FluidModel`**,
**render pipelines no longer depth test by default**, and several GUI hooks became non-abstract, so old names compile and
never run.

## Target choice & toolchain

- 26.1.2 has a stable NeoForge (stable since `26.1.2.71`; `26.1.2.130` is the newest) and an active JEI line, so it is its
  own checkpoint between the two big jumps (26.1: Java 25, no obfuscation, templates, registries-bound stacks, GUI
  `extract*` rename; 26.2: the rendering rewrite = M8).
- **Java 25** (`temurin25-jdk`, `JAVA_HOME` in the same command as Gradle — see [`COMMANDS.md`](../COMMANDS.md#2612-notes-m7)).
  NeoGradle **7.1.39** + Gradle **9.2.1** + foojay `1.0.0` are unchanged: the official `MDK-26.1.2-NeoGradle` uses the
  same, with toolchain 25 and no mappings config. NeoForm `26.1.2-1`, FML `11.0.15` (`loader_range=[4,)` still fine).
- **No Parchment**: the `parchment` block and the Tinkers Parchment plugin repository are removed. Parameter names are
  Mojang's own.
- **Lombok pinned to `1.18.42`** (`lombok { version = … }` in both `build.gradle`): the freefair 8.6 default, 1.18.32,
  crashes javac 25 with `NoSuchFieldException: com.sun.tools.javac.code.TypeTag :: UNKNOWN`. If another javac 25 issue
  shows up, bump the plugin (9.x) instead of adding pins.
- **Test libraries:** Mockito 5.11 (Byte Buddy 1.14) cannot instrument Java 25 classes → **Mockito `5.20.0`** (Byte Buddy
  1.17.7); **JaCoCo `0.8.14`** (Java 25 class files).
- Harmless noise: `neoFormRecompile` warns about 11 vanilla `[removal]` uses; the JST step prints `sun.misc.Unsafe`
  warnings on Java 25.
- `runClientHotswap` needs a JetBrains Runtime 25 (DCEVM) registered in `org.gradle.java.installations.paths` (D-HOTSWAP:
  installed by hand when needed; only JBR 21 is on the machine).
- Pins: Crafting Tweaks `26.1.2.4`, Balm `26.1.2.15`, **kuma-api runtime pin `26.1.2.4`** (Balm's POM pins `26.1.2.2`,
  which crashes the client — see [Compat](#compat-jei-29-crafting-tweaks-json-things)), JSON Things `0.18.5`, JEI
  `29.54.0.123` (+ the separate `mezz_config` mod). Immersive Engineering stays excluded.
- **jsr305 still ships** (NeoForm `26.1.2-1` library list), but neither repo needs it any more: the `javax.annotation` →
  JSpecify `@Nullable` migration was done before the port, on `1.21.11` (D-N2, Phase 0.6, see below).

## Mechanical renames: jar diff + compiler-driven applier (D-TOOL)

26.1 ships unobfuscated, so the old and new NeoForm `raw.jar` are both Mojang-named and can be diffed class by class. The
renames are **derived from the jars, never written by hand**. Tools in `repo/scripts/rename-map/` (single-file Java 25
programs using the JDK `java.lang.classfile` API, plus PowerShell wrappers; commands in
[`COMMANDS.md`](../COMMANDS.md#mechanical-renames-between-versions-rename-map), details in the folder's README):

1. **`Find-ApiRenames.ps1`** (`FindApiRenames.java`): jar-to-jar API diff, ~4 s for 10k classes. Generates
   `maps/26.1.2.txt` (class rules for `Invoke-RenameMap.ps1`, new rule kind `class` = simple name only where the old class
   is imported) and `maps/26.1.2-members.tsv` (member table: 598 methods + 151 fields + 1 hint) from the hand-maintained
   **`maps/26.1.2.overrides.txt`**. 179 class pairs (77 renamed, 102 moved); every semantic swap is printed as a `WARNING`
   ("same simple name, different shape").
2. **`Invoke-RenameMap.ps1`** with the class map (own commit).
3. **`Invoke-CompilerRenames.ps1`** (`CompilerRenames.java`): reads the flow-gate compile log (`flow.init.gradle`, so javac
   reports method-body errors past the first failure) and the member table, and edits **only the lines javac reported**:
   (a) `cannot find symbol` member calls whose receiver type (or a supertype) maps `X → Y`, (b) `method does not override`
   declarations whose supertype method was renamed. It reports unresolved overrides (with the overrides file's `hint`),
   ambiguous spots, descriptor-only matches to review once, and possible dead overrides. Loop compile → apply until it
   reports `edits=0`. Tinkers passes `-Root "<tinkers>,<repo>"` so Mantle supertypes are indexed.

Member renames by name alone would over-match (`getId`, `getValue`, `draw` collide), and GUI renames depend on the receiver
(`drawString` → `text`, `render*` → `extract*`), so they must go through the compiler. Most of them only appear after the
class pass (calls on an unresolved `GuiGraphics` report nothing).

| Step (unique errors, flow gate) | Mantle | Tinkers |
|---|---:|---:|
| Baseline | 770 / 90 files | 1246 / 285 files |
| Class map | 237 (104 rules, 48 files, 374 hits, 0 string hits) | 647 (107 files, 575 hits, 0 string hits) |
| Applier passes | 206 → 204 (38 + 2 edits, third pass 0) | 570 → 568 (75 / 7 / 2 edits, fourth pass 0) |
| Access transformer | 192 | 563 |
| Hand fixes | 0 | 0 |

**The overrides file** (`class` / `method|field` / `hint` / `rule` lines; regenerate both maps after editing it):

- **Class pins** for semantic swaps both tools would get wrong by simple name: old `client.resources.model.Material` →
  `sprite.SpriteId` (D-SPRITE, see [Rendering](#spriteid-vs-material)), `BlockElement` → `CuboidModelElement`,
  `BlockModelPart` → `BlockStateModelPart`, `SimpleUnbakedGeometry` → `UnbakedCuboidGeometry`, `ClickType` →
  `ContainerInput`; `EmptyBlockAndTintGetter.INSTANCE` → `BlockAndTintGetter.EMPTY` as `rule literal` lines.
- **⚠️ Same-name member swaps — the jar diff can't see them.** Only members whose old name is *gone* get paired. 26.1
  renamed `RenderTypes.entityCutoutNoCull` → `entityCutout` and gave the old culled `entityCutout` the name
  `entityCutoutCull`, so an old `entityCutout(..)` call **still compiles and silently loses culling**. Forced rows pin it: a
  `method` row for the gone member (`override`) and one for the member that still exists (`override-swap`: documents the
  swap and **reserves the target** — a forced target is never paired again); `-` as the new name means removed (never
  paired). `entitySmoothCutout` → `endCrystalBeam` is pinned the same way. The callers of the still-existing name must be
  switched by hand (Tinkers `CombatFishingHookRenderer` → `entityCutoutCull`).
- **`hint` rows** for removed supertype methods with no successor: `renderBg` (parameters reordered, merged into the
  non-abstract `Screen#extractBackground` — see [GUI](#gui)). The applier prints the hint; it never auto-renames them.

**Render-type audit:** after the swap, every `RenderTypes`/`RenderPipelines`/`Sheets` use in both repos was checked against
the 1.21.11 tags and the 26.1.2 pipelines' `withCull`: `SlimeskullArmorModel` `entityCutoutNoCullZOffset` →
`entityCutoutZOffset`; `Sheets.cutoutBlockSheet()` = `entityCutoutCull(blocks)` = the old `entityCutout(blocks)`; no other
swap.

### ⚠️ Access transformers

Still not touched by any rename tool; `Find-StaleAccessTransformer.ps1` against the 26.1.2 `raw.jar` found Mantle 1 / 9 and
Tinkers 5 / 108 stale entries (`GameRenderer.guiRenderState` → `getGameRenderState()` is public, `renderSlot` →
`extractSlot` in `AbstractContainerScreen` and `Gui`, `Sheets.SHIELD_MATERIALS` → `SHIELD_SPRITES`, `ItemFrameRenderer
.blockRenderer` and `FireworkStarRecipe.SHAPE_BY_ITEM` gone). Private members are not in the member table, so calls to
access-transformed private methods are renamed by hand.

**⚠️ Each repo compiles against its own AT only.** Each NeoForm setup applies only that repo's AT, so Mantle's
`protected-f imageWidth/imageHeight` and its `BlockEntityRenderState blockState` entry don't reach Tinkers at compile time:
Tinkers repeats them (`public-f` / `public`). At runtime NeoForge merges every mod's AT. Changing a Mantle AT entry re-runs
the Mantle NeoForm setup (~8 min).

### JSpecify `@Nullable` (D-N2, done on `1.21.11` first)

`Convert-NullableToJSpecify.ps1` (dry run by default, 38 self-tests) rewrote `javax.annotation.Nullable` → type-use
`org.jspecify.annotations.Nullable` with the placements javac needs (`Outer.@Nullable Inner`, `String @Nullable []` for a
nullable array), removed `@Nonnull` (packages are `@NullMarked`), `CheckForNull` → `@Nullable`, and kept a `@Nonnull` field
in a Lombok-generated constructor/setter as `lombok.NonNull` (Lombok generates the null check from it). Mantle 157 files,
Tinkers 628 files; **0 `javax.annotation` left**; `javap -c -p` of every class before/after identical (Lombok null checks
unchanged). Done on `1.21.11` with its green battery, then merged into `26.1.2`. New code imports
`org.jspecify.annotations.Nullable` (an IDE can still auto-import the jsr305 one while NeoForm ships it).

## Component binding: stacks need bound data components (the core 26.1 hazard)

- `Holder.Reference#components()` throws **"Components not bound yet"** until the default data components are bound. They
  are bound only at the **end** of every datapack (re)load (`ReloadableServerResources#updateComponentsAndStaticRegistryTags`,
  after every reload listener — recipes included — has run; then NeoForge posts `DefaultDataComponentsBoundEvent`) and on
  client registry sync. **Datagen never binds them**, and neither does a plain unit-test bootstrap.
- `new ItemStack(holder, count[, patch])` and NeoForge `new FluidStack(..)` call `components()`. `ItemStack.CODEC` /
  `FluidStack.CODEC` refuse unbound holders ("Item `<id>` does not have components yet"). `EMPTY` is safe.
- **So mod construction, registration events, static initializers, recipe/loot/advancement decoding, datagen and unit tests
  cannot build stacks.** A decoder that tries is not a crash: `SimpleJsonResourceReloadListener` logs `Couldn't parse data
  file …` and **skips the file** — recipes vanish silently.
- Data and decode paths use templates instead: vanilla `record ItemStackTemplate(Holder<Item>, int count,
  DataComponentPatch)` (non-empty; `CODEC` also accepts a bare id; `create()` validates and **logs + returns `EMPTY`** on an
  invalid patch) and NeoForge `record FluidStackTemplate(Holder<Fluid>, int amount, DataComponentPatch)`. Both
  `MAP_CODEC`s **omit `count`/`amount` when it is the default** (see [count 1](#recipes-and-loot)).

### Rules we followed

- **D-TPL — Mantle's own types stay the boundary.** `ItemOutput` / `FluidOutput` hold a template (or item/fluid + count)
  and **build a new stack on every `get()`**, so no stack outlives a reload (tag outputs cache the preferred item/fluid, not
  a stack). New `*_TEMPLATE` loadables decode the **same JSON** into templates: `ItemStackLoadable.REQUIRED_ITEM_TEMPLATE` /
  `REQUIRED_STACK_TEMPLATE` / `REQUIRED_ITEM_NBT_TEMPLATE` / `REQUIRED_STACK_NBT_TEMPLATE`, `FluidStackLoadable
  .REQUIRED_STACK_TEMPLATE` / `REQUIRED_STACK_NBT_TEMPLATE`. The stack loadables stay for runtime NBT and network, where
  components are bound. `ItemOutput.fromTemplate` / `FluidOutput.fromTemplate` for datagen. Mantle's `ItemOutput` JSON stayed
  byte-identical. Most Tinkers call sites didn't change (outputs are still `Supplier`s); vanilla templates appear only where
  vanilla forces them (recipe display, `ShapedRecipe` results, crafting remainders, which are nullable templates now).
- **D-STATIC — no stack in static init or registration.** Mantle `ContentSmelting.FUELS` (28 stacks in a book page
  `<clinit>`) builds on use; gametest constants (`LAVA`, smeltery resources) are built per test (gametest classes
  initialize when the tests register, before any datapack load); Tinkers `CrystalshotModifier` built a stack in
  `registerHooks`; Mantle `EdibleItem`'s constructor read `components()` (dropped) — that one stopped the mod from loading.
  The cauldron `Dispatcher#get(ItemStack)` needs a stack at common setup, so Tinkers reads the dispatcher's item map through
  an AT instead.
- **Guard:** unit **`NoStacksInStaticInitTest`** (ASM scan of every Mantle/Tinkers `<clinit>` and the same-class methods it
  reaches: stack constructors, calls returning a stack, `ItemResource/FluidResource.of`, codec `parse`/`decode`). Written on
  `1.21.11` with a `KNOWN` list = the expected-red list of 26.1.2; the port emptied it (a stale entry fails the test).
- **D-DATAGEN — bind the components in data runs.** Mantle **`DatagenComponents.bind(lookup)`** (overloads for a
  `HolderLookup.Provider` and a `CompletableFuture` of one) runs `BuiltInRegistries.DATA_COMPONENT_INITIALIZERS
  .build(lookup)` + `apply()` with every tag lookup answered by a **bound empty `HolderSet.Named`** (Mantle AT opens its
  constructor and `bind`; datagen lookups answer `HolderSet#emptyNamed` placeholders, which NeoForge's component
  validation rejects). Call it from a `GatherDataEvent` listener before providers run. Tinkers calls it in
  `gatherDataServer` with `datapackRegistryProvider.getRegistryProvider()` (Tinkers trim materials are referenced by item
  components). This covered every stack-building provider (tool render stacks in advancements and station layouts, filled
  tank and slimesuit icons, part display stacks) with **no provider change and byte-identical output** apart from the
  count-1 omission. The client data run needs no binding. Tag-based default components (e.g. `DamageResistant` from
  `#is_fire`) are empty there.
- **D-TESTBOOT — unit tests bind too.** **`BaseMcTest#bindDefaultComponents`** = the same recipe over the built-in
  registries + `VanillaRegistries.createLookup()`, every lookup wrapped so a missing/unbound tag becomes a bound empty
  `HolderSet.Named` (package-private constructor + `bind` via reflection). Call it after `Bootstrap.bootStrap()` **and
  after registering test items** (`MaterialItemFixture`, `ToolItemTest`, `ToolHarvestLogicTest`). No test had to move to a
  gametest; tag-based default components are empty in unit tests.
- **Load-time paths that look client-only:** item models load before the client binds components, so Tinkers'
  `FluidContainerModel` `contained_fluid` is a `FluidStackTemplate` (same JSON; a `FluidStack` codec failed every bucket
  model at startup); station layout item icons (`LayoutIcon`) hold an `ItemStackTemplate`; Mantle
  `TextureColorHelper#getItemColor` returns `-1` (uncached) before components are bound (a resource reload on the title
  screen hit it).
- **Advancements decode before binding too:** exact `tconstruct:tank_fluid` predicates and filled-tank icons decode a
  `FluidStack` (`SimpleFluidContent`), so `foundry/blaze`, `foundry/manyullyn_lanterns` and `plate_armor` were dropped on
  every server start. New item sub-predicate `tconstruct:tank_fluid` (id + amount + optional components, stack built when
  matching); the icons are **empty tanks** now (see [Known issues](#known-issues-as-of-m7)). Guards
  `datapack_advancements_complete`, `tank_fluid_advancement_criterion_matches`.
- **Stale stacks across reloads:** components are re-bound per load. `ItemStack#getPrototype()` is the holder's *current*
  components, so an identity check against it can't detect a stale cached stack — drop caches from reload listeners
  instead (Tinkers `EnchantmentConvertingRecipe` tool list now clears through `RecipeCacheInvalidator`, gametest
  `enchantable_tools_cache_drops_on_reload`; JEI solid fuels built per call). A rebind with equal components keeps the same
  map.

**Guards for the decode side (R1, written on `1.21.11` before the port):** `DatapackCompletenessGameTests` —
`datapack_recipes_complete` (every recipe JSON whose `neoforge:conditions` pass is in the `RecipeManager`, and nothing else;
2097 files), `datapack_loot_tables_complete` (346), `datapack_loot_modifiers_complete`, and `datapack_advancements_complete`
(added in Phase 4). Each was mutation-checked with a broken JSON.

## Recipes and loot

- **`RecipeSerializer` is a final record** `(MapCodec<T> codec, @Deprecated StreamCodec streamCodec)`: no subclassing.
  Mantle `LoadableRecipeSerializer` and `SimpleRecipeSerializer` became factories (`LoadableRecipeSerializer.of(loadable)`
  → `RecipeSerializer<T>`, `.of(loadable, type)` → `TypeAwareRecipeSerializer<T>`, `SimpleRecipeSerializer.of(constructor)`);
  the loadable context is built on first decode. **`TypeAwareRecipeSerializer` is a record `(serializer, typeSupplier)`**:
  register its `.serializer()` (Tinkers `TinkerModule#registerTyped(name, factory)` memoizes the pair). The stream codec is
  `@Deprecated` but recipe sync still exists (`ClientboundUpdateRecipesPacket`, NeoForge `RecipesReceivedEvent`), so keep
  `synced_recipes_stream_codec_round_trip`.
- **`Recipe#assemble(T input)`** lost the `HolderLookup.Provider`. Mantle `ICommonRecipe` / `ICustomOutputRecipe` default
  `assemble(C)`; `getResultItem(HolderLookup.Provider)` is kept for source compatibility (the default passes
  `RegistryAccess.EMPTY`; no Tinkers recipe reads it).
- **`Recipe#group()` and `showNotification()` are abstract.** Mantle **`ICommonRecipe` defaults them to `""` / `true`**
  (the 1.21.11 vanilla defaults), so the 39 Tinkers recipe classes without a book-info base compile and behave as before.
- Vanilla ctors: `ShapedRecipe(Recipe.CommonInfo, CraftingRecipe.CraftingBookInfo, ShapedRecipePattern,
  ItemStackTemplate)`. Mantle `ShapedFallbackRecipe` / `ShapedRetexturedRecipe` expose `CODEC` / `STREAM_CODEC` constants
  (nested `Serializer` classes gone). Tinkers' material crafting recipes build on `ShapedRecipe/ShapelessRecipe.MAP_CODEC`.
- **Cooking result recipes** (Mantle smelting/blasting/smoking/campfire with an `ItemOutput` result): the vanilla parent
  needs a non-empty result template, so they pass an `Items.BARRIER` placeholder and replace `assemble` and `display`.
  JEI 29's cooking categories read `display()`, so the barrier never shows (uitest `jei_mantle_cooking_no_barrier`); the
  result slot stays empty, as in 1.21.11.
- Cooking datagen builders take an explicit `CookingBookCategory`; `SingleItemRecipeBuilder.stonecutting` takes the count.
- **`count: 1` is dropped from data.** Results and icons written through `ItemStackTemplate` codecs omit a count of 1
  (`ItemStack.MAP_CODEC` wrote it): 190 Tinkers recipes and 41 advancements lost `"count": 1` on regeneration. Both forms
  read the same. Mantle's own `ItemOutput` JSON keeps writing the count it always wrote.
- **Mantle `set_fluid` (`SetFluidLootFunction`)** holds a `FluidStackTemplate` (loot tables decode before fluid components
  are bound); `builder(FluidStackTemplate)`. The codec is pinned by unit tests: an empty fluid, a missing fluid or amount 0
  **fail to parse** (same as the 1.21.11 `FluidStack.CODEC`); **a bare fluid id parses as 1000 mB** (new, from the template
  codec). A template cannot be empty, so the test's old empty-fluid case is gone.
- **Loot types are gone.** `LootItemConditionType` / `LootItemFunctionType` / `LootPoolEntryType` were removed: the
  registries hold `MapCodec`s directly and loot objects override `codec()` instead of `getType()`. Mantle `MantleLoot`
  holders are `DeferredHolder<MapCodec<? extends X>, MapCodec<Y>>`; `TagEmptyCondition` / `TagFilledCondition` (both an
  `ICondition` and a loot condition) return their concrete `MapCodec`. `LootContextParams.TOOL` is an `ItemInstance`: read it
  as an `ItemStack` only when it is one.
- **⚠️ An unknown tag in an ingredient is now a decode failure.** 26.1's reload lookups only know the tags loaded in that
  reload, so `#c:ores/tin` with no mod defining it fails with **"Missing tag"** and drops the whole file (1.21.11 decoded it
  as an empty tag). It hit 12 Tinkers compat GLMs (`lustrous/*`). Mantle **`RegistryJsonOps.lazyTags(ops)`** answers a
  missing tag with a lazy unbound named set (matches through the holder's tags — nothing until defined, then its contents;
  encodes back as `#tag`); `mantle:contains_item` uses it. It returns a plain `RegistryOps` over `JsonOps`, **dropping any
  wrapper** (e.g. NeoForge `ConditionalOps` and its context), so wrap only the ops where the tag is decoded. Use it only for
  predicates: the set's contents can't be listed. Guard: unit `ContainsItemModifierLootConditionTest`.
- **⚠️ NeoForge dropped `global_loot_modifiers.json`.** `LootModifierManager` is a plain `SimpleJsonResourceReloadListener`
  over `loot_modifiers/` (every file loads) and the provider no longer writes the index. The **order is the `priority`
  field, highest first** (`comparingInt(-priority)`, verified in bytecode), **ties in hash order**. The `LootModifier` ctor
  takes the priority; Mantle's GLMs read it in `codecStart` (written only when not the default). Use explicit priorities when
  order matters: Mantle **`AbstractLootModifierBuilder#priority(int)`**, `GenericLootModifierBuilder(conditions, priority)`.
  Tinkers counts down from 1000 in the old index order (wither_bone 1000 … cadmium 980; data diff = only `priority`
  fields). Guards: `loot_modifiers_keep_the_old_order`, `datapack_loot_modifiers_complete` / `ore_loot_modifiers_load` (read
  the manager through `NeoForgeReloadListeners.LOOT_MODIFIERS_KEY`, no index file).
- Vanilla `minecraft:firework_star` is a new data-driven recipe whose `STREAM_CODEC` decodes the shapes into a `HashMap`
  keyed by an enum, so a decoded recipe re-encodes with permuted entries. The round-trip test re-encodes both with an
  `EnumMap` and compares byte for byte (exempted per serializer, with the reason).

## Trades as data (wandering trader ancient tool)

`VillagerTrades.ItemListing` and NeoForge `WandererTradesEvent` are gone: trades are datapack **`VillagerTrade`** registry
entries, offered through **trade tags** (vanilla picks from `#minecraft:wandering_trader/uncommon` without duplicates). A
trade may carry a **`merchant_predicate`** (a loot condition); a failed predicate gives a `null` offer, which is removed and
another entry drawn (verified in `AbstractVillager#addOffersFromItemListingsWithoutDuplicates`).

- Tinkers' ancient tool trade: loot function **`tconstruct:ancient_tool_trade`** (`AncientToolTradeFunction`: random
  `#tconstruct:modifiable/wandering_trader` tool with ancient materials, the 1.21.11 tier cost formula set as
  `ADDITIONAL_TRADE_COST`); trade entries `tconstruct:ancient_tool_1` … `_6` (`gives` a placeholder `tconstruct:war_pick`
  that the function replaces, `wants` emerald count 0 + the cost, `max_uses` 1, `xp` 15, `reputation_discount` 1.0) in
  `#minecraft:wandering_trader/uncommon`; generated by `VillagerTradeProvider` + `VillagerTradeTagProvider`.
- **Config weight → N weighted copies.** `wanderer_ancient_tool_weight` keeps its 0–100 range, but copy *k* is gated by
  `merchant_predicate` `tconstruct:config` prop `wanderer_ancient_tool_k` (weight ≥ *k*), so the weight is **effectively 0–6
  (above 6 saturates at 6)**. Default 6 copies among the 15 vanilla uncommon entries with 2 draws gives P = 1 − C(15,2)/C(21,2)
  = **50 %, the 1.21.11 chance**. Packs can also edit the tag.
- **A trade with no cost gives no offer.** 1.21.11 still offered an all tier-0 tool for 0 emeralds; 26.1 drops it. The cost is
  clamped to **≥ 1 emerald**.
- Guards: `TradeGameTests` — `ancient_tool_trade_loaded`, `ancient_tool_trade_copies_follow_weight` (6 → all, 2 → copies
  1–2, 0 → none, 100 → all), `ancient_tool_trade_offer`, `ancient_tool_trade_cost_minimum`.

## Rendering

### Per-quad render layers; `render_type` removed

- `record BakedQuad(position0..3, packedUV0..3, Direction, BakedQuad.MaterialInfo, BakedNormals, BakedColors)` moved to
  `client.resources.model.geometry`. **`MaterialInfo(sprite, ChunkSectionLayer layer, RenderType itemRenderType, tintIndex,
  shade, lightEmission, ambientOcclusion)` carries the render layer per quad**; `MaterialInfo.of(Material.Baked,
  Transparency, …)` picks the layer from the sprite's transparency and the item render type from the atlas (blocks →
  `Sheets.translucent/cutoutBlockItemSheet()`, else `translucent/cutoutItemSheet()`).
- NeoForge **`RenderTypeGroup` and `NamedRenderTypeManager` are gone, and with them the `render_type` key of the model
  format** (no JSON key, no named types). `ItemBlockRenderTypes` is removed. A JSON `render_type` is now ignored by
  everyone. **Block quads follow the texture alpha.** To force a texture translucent, use the 26.1 model material flag
  **`{"sprite": …, "force_translucent": true}`** (vanilla's material baker keeps it on `Material.Baked`).
- Mantle element models bake every face through **`ModelHelper.bakeQuad`** (= vanilla `FaceBakery`, with
  `UNCACHED_INTERNER` outside the bakery) and keep `force_translucent` on every bake path (lookups return `Material.Baked`).
  Mantle fluid textures gained an optional `force_translucent` (still/flowing/overlay). Item layer quads keep Mantle's
  1.21.11 default (translucent, NeoForge unsorted translucent item type per atlas). The M6 per-atlas item layer split
  (`addItemLayers`) collapsed into **one layer with per-quad item render types**; items pass their transformation
  (`ItemModel.Unbaked#bake(BakingContext, Matrix4fc)`) to `addItemLayer`.
- Tinkers deleted `FluidClientEvents`' `ItemBlockRenderTypes.setRenderLayer` calls: the fluids it forced translucent (honey,
  the 3 slimes, molten diamond/emerald/glass/amethyst, liquid soul) have translucent pixels anyway; **molten soulsteel is
  fully opaque → now solid** (looks the same). No `force_translucent` was needed.
- **Visual decision (user, 2026-11-27): accept the 26.1 behaviour, no force-opaque fallback.** Compared side by side with
  the 1.21.11 reference run: **retextured blocks with translucent textures (ice/slime/honey stations) turn from opaque to
  translucent**; **the seared lantern now shows its fluid** (1.21.11 showed it empty); tank fluids are slightly more
  transparent (drawn by the block entity renderer, not the old `cutout` model quads); slime leaves edges marginally softer;
  gauges, GUI items, glass and the lava tank unchanged.
- Guards: uitest `translucent_item_layers` (ice repair kit vs stone over red/blue bands: blended pixels vs 0),
  `force_translucent_bake` (`force_translucent` reaches Mantle's runtime bake: TRANSLUCENT vs SOLID faces),
  `render_layer_review` / `render_layer_review_items` (the decision scenes).

### `SpriteId` vs `Material`

- **⚠️ Name reuse.** The old `client.resources.model.Material` (atlas + texture) is now **`record SpriteId(Identifier
  atlasLocation, Identifier texture)`** (`renderType(fn)`, `buffer(…)`), while a **new** `client.resources.model.sprite
  .Material(Identifier sprite, boolean forceTranslucent)` + `Material.Baked(TextureAtlasSprite, boolean)` is the atlas-less
  *model texture reference*. A same-simple-name class map sends old users to the wrong class (D-SPRITE pin in the overrides
  file). `MaterialMapper` → `SpriteMapper`; `Sheets.SHIELD_BASE` & co. return `SpriteId`.
- Raw model texture maps hold `Material`; runtime lookups go through Mantle `ModelHelper.getMaterial(Material)` /
  `getSprite(Material)` (blocks atlas, then items, like the bakery; the M6 `block_or_item` pseudo atlas is gone);
  `getSprite(SpriteId)` stays for concrete atlases. Particles come from `particleMaterial()` / `BlockStateModelSet`.
- Model classes regrouped into `client.resources.model.{geometry, sprite, cuboid}` and `client.renderer.block.dispatch`
  (`BlockElement` → `CuboidModelElement`, `BlockElementFace` → `CuboidFace`, `BlockModelPart` → `BlockStateModelPart`,
  `SimpleUnbakedGeometry` → `UnbakedCuboidGeometry`, `BlockModelWrapper` → `CuboidItemModelWrapper`, …) — all by the class
  map.

### Fluid models (`FluidModel` / `FluidRenderInfo`)

- `IClientFluidTypeExtensions#getStillTexture/getFlowingTexture/getTintColor` are **removed**. Fluid client data is a
  **`record FluidModel(ChunkSectionLayer, Material.Baked still, flowing, @Nullable overlay, @Nullable FluidTintSource,
  @Nullable CustomFluidRenderer)`**, registered as `FluidModel.Unbaked` in NeoForge **`RegisterFluidModelsEvent`** (mod bus)
  and baked into `ModelManager#getFluidStateModelSet()`. Stack tint → `FluidTintSource#colorAsStack(FluidStack)`. A fluid
  without a model renders the missing model and logs `Missing FluidModel for fluid …`.
- Mantle registers one model per fluid of each texture fluid type (`MantleClientFluidTypes`,
  `ClientTextureFluidType#createFluidModel()`) from the **unchanged fluid texture JSON**. `FluidTextureManager` now loads in
  `prepareSharedState` (models bake in parallel during the model manager's preparation). `FluidRenderInfo.of(FluidStack)`
  (the R3 seam) resolves sprites and tint through `FluidRenderer.getFluidModel(fluid)` + `colorAsStack`, so the Tinkers
  callers (tank/fluid texture/container/modifier models, `GuiUtil`, `FluidParticle`) only switched to it. Fluid particle
  layer `TERRAIN` → `TRANSLUCENT_TERRAIN`.
- Vanilla `LiquidBlockRenderer` is now `net.minecraft.client.renderer.block.FluidRenderer`; it clashes by simple name with
  Mantle's `FluidRenderer` only in a file that imports both (none).
- Guard: uitest `melter_tank_tint` (GUI tank tint pixel assert), plus `smeltery_tank_world`, `fluid_blocks`, `casting_*`.

### ⚠️ Render pipelines need an explicit depth state

26.1 `RenderPipeline` builders default to **no depth stencil state = no depth test** (up to 1.21.11 the default tested and
wrote depth). Mantle's fluid and book structure pipelines set none, so every fluid-renderer fluid (tanks, smeltery,
casting, faucets) drew over the blocks in front of it, a tank's own frame included. Fix: `.withDepthStencilState(
DepthStencilState.DEFAULT)`. A pipeline that must ignore depth (Tinkers' smeltery error block) passes
`withDepthStencilState(Optional.empty())` (vanilla's GUI text snippet pattern). Guard: uitest `fluid_depth_test` (honey tank
behind stone must not show; a second honey tank beside it must show — mutation-checked).

- **`LightTexture` split:** `Lightmap` (texture + `render(LightmapRenderState)`, static `getBrightness(DimensionType,

## GUI

- `GuiGraphics` → **`GuiGraphicsExtractor`** (`drawString` → `text`, `drawCenteredString` → `centeredText`,
  `renderItem` → `item`, `renderTooltip` → `tooltip`, `renderOutline` → `outline`, …; `blit`/`blitSprite`/`fill`/
  `enableScissor`/`setTooltipForNextFrame`/`pose()` unchanged). Screen and widget hooks renamed to **`extract*`**:
  `render` → `extractRenderState`, `renderBackground` → `extractBackground`, `renderLabels` → `extractLabels`,
  `renderWidget` → `extractWidgetRenderState`, `renderContents` → `extractContents`, `renderSlot` → `extractSlot`. All by
  the class map + applier.
- **⚠️ `renderBg` has no successor.** It merged into `Screen#extractBackground(g, mouseX, mouseY, a)` (parameters
  reordered), which is **not abstract** and also draws the dim/blur. An old `renderBg` (or `renderLabels`/`render`) without
  `@Override` compiles and is never called. Rules:
  - direct `AbstractContainerScreen` subclasses: override `extractBackground` and call `super.extractBackground` **first**
    (dim), then draw;
  - Mantle `MultiModuleScreen` / `ModuleScreen` subclasses: override the new Mantle hook **`extractContainerBackground(g,
    mouseX, mouseY, partialTicks)`** — `MultiModuleScreen#extractBackground` draws the dim **once**, then the hook inside the
    corrected bounds (default: module backgrounds; subclasses draw, then call super where they did before);
    `ModuleScreen#extractContainerBackground` is abstract, so modules never get the dim and a missing override fails to
    compile;
  - grep for old GUI names without `@Override` after the port — subclasses overriding *their parent's* old `renderBg`
    compile fine (Tinkers `PartInfoPanelScreen` was one).
- **`AbstractContainerScreen#extractRenderState` already draws tooltips** — drop explicit `extractTooltip`/`renderTooltip`
  calls after `super.extractRenderState` (the duplicate was a no-op, first deferred tooltip wins).
- **Final fields:** `AbstractContainerScreen.imageWidth/imageHeight` are `protected final` (set by the new 5-arg
  constructor). The responsive Tinkers stations resize at runtime, so Mantle's AT makes them `protected-f` (D-SCREEN) and
  Tinkers' AT `public-f`. Vanilla values derived in the constructor (`inventoryLabelY`) don't follow later changes.
- **Screen bounds for JEI 29:** NeoForge's `getGuiLeft/getGuiTop/getXSize/getYSize` are `forRemoval` and delegate to
  `getLeftPos/getTopPos/getImageWidth/getImageHeight`, which is what **JEI 29 reads**. `MultiModuleScreen` overrides those to
  report the main window corner (side-panel slot areas were off until then; uitest `jei_crafting_station_slot`,
  `jei_smeltery_slot`). Tinkers' uitests moved to the same getters (`getHoveredSlot` for `getSlotUnderMouse`).
- **`Player#displayClientMessage(msg, boolean)`** → **`sendOverlayMessage(msg)`** (old flag `true`) /
  **`sendSystemMessage(msg)`** (flag `false`).
- `ClickType` → `enum ContainerInput`; GUI render states moved to `client.renderer.state.gui[.pip]`; `GameRenderer
  #guiRenderState` → `getGameRenderState().guiRenderState`.
- **Book export:** Mantle `/mantle book export` ran only `render`, but book content lives in the background pass, which
  `Screen#render` stopped running in 1.21.6 — exports had widgets only since M4. It now runs `extractBackground` then
  `extractRenderState`. Guard: uitest `book_export`.
- Guards for the station screens (background order, single dim, no doubled tooltip, reflow): `station_reflow`,
  `station_collapsed*`, `station_carried_clicks`, and the reference-run review.

## uitest suite behaviour changes (Mantle `UiTestSuite`)

26.1 shows screens before quick play continues, which stalled the suite until its timeout:

  `"ok"` still fails the task. Unit `UiTestSuiteTest` pins the prompt keys (from vanilla `LevelSummary.BackupStatus`) and

## Verification lessons

- **D-TOOL paid off again, with less hand work:** the jar diff found every class rename the plan had listed by hand (and
  some it hadn't, e.g. the `BlockModel` record → `CuboidModel`), and the compiler-driven applier did the receiver-dependent
  GUI renames. What it can't see is listed in the overrides file — keep it the single place for pins, swaps and hints.
- **The silent part dominated.** None of these failed to compile: recipes/loot/advancements dropped at decode (log only),
  fluids drawn through blocks (pipeline depth default), heads drawn upside down (skull transform moved), whole creative tabs
  missing (repeated stacks), JEI side-panel slot areas (deprecated getters), `renderBg` leftovers, the `entityCutout` swap,
  GLM order (index file gone). Each now has a guard.
- **Guards written before the port** (R1, Phase 0.5c, on the green `1.21.11`): datapack completeness and the static-init
  stack scan made "the recipe is silently missing" and "a stack in `<clinit>`" visible on the first 26.1.2 run.
- **The reference run found real regressions** this time (fluid depth, head items, creative tabs, JEI slot areas) — every
  PNG pair viewed side by side with the 1.21.11 release. Plus pixel/state asserts for each fix.
- **The first boot happens in datagen** — expect load blockers there (mixin targets, constructor-time component reads).
- **Link-check compat jars against the runtime library versions**, not only the compile ones (CT built on Balm 26.1.1.2
  runs on 26.1.2.15; the kuma POM pin crashed the client).
- uitest still needs an **unlocked screen** (`atio6axx.dll`).
